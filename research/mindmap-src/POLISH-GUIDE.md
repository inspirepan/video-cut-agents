# 润色规范：思维导图中文表达

这是一次**纯语言润色**任务。读者画像：软件工程师（懂 Python/Go、ffmpeg 命令行、ASR/LLM/OCR 等工程概念），但**完全不懂视频剪辑和影视制作**。现有文案有两个问题：

1. **行业黑话多**：VFR、GOP、冻结帧、drift、中间件、B-roll、卡点、Log、LUT、edit list…… 读者看不懂。
2. **电报体零碎**：缺主语、顿号长串、半句话堆砌，读起来费劲。

你的任务：把分配给你的 JSON 文件里的中文文案改得**通俗、完整、顺口**，同时**一个技术事实都不能改**。

## 只允许修改这些字段的值

- `summary`、`goal`、`interview`、`sports`、`mg`、`note`
- `inputs[]` / `outputs[]` / `points[]` 里的字符串
- `atomic[].name`（慎重，尽量不动）、`atomic[].note`
- `pitfalls[].title`、`pitfalls[].detail`
- `refs[].why`
- `title`（节点标题，**尽量不动**；只有含义严重不明时才微调，且 ≤ 16 字）

**其余一律原样保留**，一个字符都不能动：

- `id`、`tag`、`urls`、`children` 层级结构
- `atomic[].impl`（命令、库名、参数）
- `pitfalls[].source`、`refs[].repo`、`refs[].path`、`refs[].line`
- 所有数字、阈值、单位、范围（如 `0.5s`、`50/60fps`、`npl=100`、`BPM 70–90`）
- 代码标识符、字段名、命令名、模型名、文件路径（如 `r_frame_rate`、`-fps_mode cfr`、`probe.py`、`workspace.json`）

## 润色原则

### 1. 行业黑话：优先改写成大白话，改不了就加简短注解

- 能用大白话说清楚的，直接改写。例："发卡"→"明显卡顿"；"唇音不同步"→"口型和声音对不上"；"说话头"→"人物讲话特写"；"台账"→"记录文件"。
- 业内通用、改写后反而啰嗦的术语，保留原词并在**同一节点内首次出现时**加全角括号注解，注解 2–12 字。例：VFR（可变帧率）、GOP（关键帧间隔）、代理（低分辨率草稿副本）。
- 每个节点在详情面板里是独立阅读的，所以注解以"节点"为单位：同一节点内同一术语只注一次；不同节点里可以重复注。
- 注解不能编造原文没有的参数或事实，只能解释词义。
- 工程圈通用词不注：ASR、LLM、OCR、API、JSON、哈希、缓存、fps、BGM、manifest（清单即可，可不注）。

### 2. 电报体改成完整短句

- 每句有明确的主语和谓语，一句一个意思，主动语态。
- 拆掉顿号长串，该成句的成句，该分条的分层（字段本身是单字符串，不能换行分段，就在句内用句号断开）。
- 语义强度保持不变："必须"仍是"必须"，"建议"仍是"建议"。

### 3. inputs / outputs 保持名词短语

这两类是产物清单，写成简短名词短语即可，不要改成句子。只需把黑话说明白。例：

- 改前：`"内容哈希与 canonical asset 映射"`
- 改后：`"内容哈希与规范资产映射（同一内容只存一份）"`

### 4. 术语处理对照表（统一口径，避免各节点说法不一）

| 原文 | 处理方式 |
|---|---|
| VFR / CFR | 首次出现：VFR（可变帧率）/ CFR（恒定帧率）；同节点后文直接用 VFR/CFR |
| GOP | 首次出现：GOP（关键帧间隔）；或改写"关键帧间隔大"替代"长 GOP" |
| 关键帧 | 可保留；语境里读者可能误解时注（可独立解码的完整帧） |
| 冻结帧 | 改写：开头画面卡住不动 / 首帧是静止画面 |
| 代理 / proxy | 首次出现：代理（低分辨率草稿副本） |
| 中间件（指中间文件时） | **改写成"中间文件"**（视频语境的 mezzanine，不是后端中间件） |
| drift | 设备时钟漂移（录音随时间逐渐错位）；首次出现注"时钟漂移" |
| 唇音 | 口型和声音 |
| HDR / SDR | 首次出现：HDR（高动态范围）/ SDR（普通动态范围）；BT.2020/BT.709 保留不注 |
| Log（S-Log/V-Log） | 相机拍的低对比度原始格式，需要调色还原 |

| timecode | 时间码 |

| 分体设备 | 独立录音设备（与相机分开的录音笔等） |
| B-roll | 补充画面（空镜、资料镜头） |
| 口播 | 对着镜头说话 |
| 花字 | 装饰性字幕 |
| 压角标 | 在角落叠加 logo |
| 卡点 | 让剪辑点对齐音乐节拍 |
| drop | 音乐高潮点 |
| beat grid | 节拍网格 |
| hook | 开头几秒的吸引点 |
| cold open | 正片前的高潮前置片段 |
| J-cut / L-cut | 声音先入 / 声音延后的剪法（或直接改写语义） |
| 闪白 / 闪黑 | 白场 / 黑场过渡 |

表里没有的术语，按原则 1 自行处理；拿不准语义的就保守处理（保留原词加注解，不要猜改）。

### 5. 长度上限（比生成期略放宽，用来容纳注解；不要超过）

- `title` ≤ 16 字；`summary` ≤ 55 字；`goal` ≤ 140 字
- `interview` / `sports` / `mg` ≤ 110 字
- `inputs[]` / `outputs[]` 每条 ≤ 45 字
- `points[]` 每条 ≤ 90 字
- `atomic[].name` ≤ 14 字；`atomic[].note` ≤ 85 字
- `pitfalls[].title` ≤ 20 字；`pitfalls[].detail` ≤ 170 字
- `refs[].why` ≤ 55 字

## 改写示例（照这个口味来）

**goal 改前：**
> 长访谈和赛事原片常是 VFR、HDR、带旋转、多音轨的大文件。直接剪会音画漂移、切在冻结帧、缓存失效。这一步产出探测 manifest、内容哈希、统一时间基准和阶段 checkpoint。

**goal 改后：**
> 长访谈和赛事原片通常是大文件：帧率不固定（VFR）、高动态范围（HDR）、带旋转标记、有多条音轨。不做预处理就直接剪，声音和画面会逐渐错位，切点可能落在错误的帧上，缓存也会失效。这一步产出探测清单（manifest）、内容哈希、统一的时间基准和各阶段的断点存档（checkpoint）。

**interview 改前：**
> 多机位加外接麦克风。超过 10 分钟的分体设备录音必须做 drift 校正，否则一小时后唇音明显不同步。

**interview 改后：**
> 访谈常有多台相机和外接麦克风。独立录音设备工作超过 10 分钟会出现时钟漂移，必须先校正；否则录到一小时左右，口型和声音会明显对不上。

**pitfalls[].detail 改前：**
> 无损切只能落在关键帧上，长 GOP 下实际起点可能早 1–10 秒，文件能播但首帧是错的。偏差超过 0.5s 就必须改成重编码。

**pitfalls[].detail 改后：**
> 不重编码的切法只能从关键帧（可独立解码的帧）开始。关键帧间隔大时，实际起点可能比指定时间早 1–10 秒：文件能播放，但开头画面是错的。偏差超过 0.5s 就必须改成重新编码。

**atomic[].note 改前：**
> 同哈希复用已有资产与派生缓存，不同内容同名直接报错

**atomic[].note 改后：**
> 内容哈希相同的文件直接复用已有资产和派生缓存；文件名相同但内容不同则直接报错

**refs[].why 改前：**
> VFR 判定阈值与 probe 字段的真实实现

**refs[].why 改后：**
> VFR 判定阈值和探测字段的真实实现

## 工作流程

1. 通读分配给你的整个 JSON 文件（文件较大就分段读完，必须读完全部）。
2. 用 Edit 逐字段修改。不要重写整个文件，不要调整缩进和字段顺序。
3. 改完后必须验证 JSON 合法：`python3 -c "import json; json.load(open('文件路径'))"` 无报错。
4. 自检一遍：有没有误改 impl/source/path/line/urls？有没有把"必须"改成"建议"之类的强度漂移？有没有漏掉明显黑话？
5. 最终回复只需 150 字以内：改了多少处、有没有拿不准的地方。
